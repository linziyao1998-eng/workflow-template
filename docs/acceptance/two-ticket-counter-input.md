# 双 Ticket 串行工作流验收输入（待人工确认）

此文件是本次工作流验收的候选需求输入，不是已批准的 Spec 或 Ticket 计划。`workflow-clarify-spec` 应以本文件的明确版本为输入，核对缺口后展示完整待发布内容，等待人工批准。后续两个阶段也分别由人工调用。

## 背景与目标

当前示例计数器只能增加和重置。本次增加“减少”和“撤销上一步”，同时用两个有真实依赖关系的 Ticket 验证串行执行、原生 Issue 依赖关系和 PR 合并后的 Issue 关闭行为。

## 产品需求

1. **A：减少计数。**在现有操作区增加“减少”按钮。点击或用键盘激活时，计数减 1，最低为 0；为 0 时按钮禁用。现有“增加”“重置”和刷新归零行为继续有效。
2. **B：撤销上一步。**在 A 完成的计数器上增加“撤销”按钮，支持撤销最近一次实际改变计数的“增加”“减少”或“重置”。一次撤销恢复操作前的计数，然后撤销记录清空；撤销本身不能再次撤销。没有可撤销记录时按钮禁用。未改变计数的操作不产生记录；撤销后发生新的计数变化时，以该变化建立新的单步记录。刷新后计数和撤销记录均清空。

## 界面与范围

- 交互参考现有 `src/App.vue` 的语义按钮、实时输出和禁用状态；视觉参考现有 `src/style.css` 的按钮、焦点和页面样式。候选排列为“增加、减少、重置、撤销”；在 320px 宽度下允许按钮换行，保持现有配色和字号。
- 新按钮使用上述中文可访问名称，支持 Tab 聚焦和 Enter/Space 激活，禁用时不能改变计数。计数变化继续由现有带 `aria-live` 的输出呈现。
- 仅修改当前页面内的示例计数器；不增加持久化、服务端接口、路由、全局快捷键或多步历史。

## Ticket 边界与依赖

仅拆成两个可分别验证的 Ticket：A 实现减少及其验证；B 实现覆盖三种计数变化的单步撤销及其验证。B 的验收包含撤销“减少”，因此 **B blocked by A**。两个 Ticket 都应成为同一父 Spec Issue 的原生 sub-issue；B 与 A 还应建立 GitHub 原生 `blocked by` 关系，不能仅在正文里写依赖。

## 可观察的产品验收

- A：从 0 开始，“减少”禁用；增加两次后减少一次显示 1；再减少一次显示 0，“减少”和“重置”均禁用；键盘操作有效；刷新后显示 0。
- B：从 0 增加到 1 后撤销回 0；增加到 2 后减少到 1，再撤销回 2；从非零重置到 0 后撤销回原值。每次撤销后“撤销”禁用，直到又有实际计数变化；刷新后“撤销”禁用。
- A 集成后的 `npm run check` 和适用的 Chromium E2E 通过，才算 A 已验证；B 完成后按同样门禁验证。最终独立 review 和 `npm run check:all` 覆盖 PR 的最终提交。

## 工作流观察点

1. 票集发布后：父 Issue、A、B 均为 Open；A 和 B 是原生 sub-issue；B 的原生 `blocked by` 指向 A。保存关系界面或 API 读回证据。
2. A 代码提交但尚未集成验证时：B 仍 blocked，B 不应开始。A 集成且验证通过后：执行 skill 自动移除 B→A 的原生阻塞关系，并记录移除前后状态；A、B 和父 Issue 仍为 Open。这里的“自动”指 `workflow-implement-tickets` 执行该步骤，不假定 GitHub 自己在提交代码时解除依赖。
3. B 验证、独立 review 和最终门禁通过后：正式 PR 指向仓库默认分支，PR 正文分别包含父 Issue、A、B 的有效 `Closes #N` 引用。PR 由人审查；合并前三个 Issue 均为 Open。
4. 人工 review 并合并 PR 后：在 GitHub 读回父 Issue、A、B 均为 Closed，并确认关闭事件关联该 PR。仅有原生父子关系并不足以保证父 Issue 自动关闭，因此三个 Issue 都须有各自的关闭引用。

## 人工暂停点

- 本输入经人工确认后，人工调用 `$workflow-clarify-spec`；在完整 Spec 内容和版本等待批准时暂停。
- Spec 发布且读回通过后，人工调用 `$workflow-plan-tickets`；在完整双 Ticket 计划等待批准时暂停。
- 票集、原生关系和标签读回通过后，人工调用 `$workflow-implement-tickets`；在正式 PR 产生后暂停，等待人工 review 与 merge。
- merge 后只做 Issue 状态和关闭事件的读回验收，不代替人工合并。
