# 工作流交付验证

## 本轮范围

自有 workflow skills、common、配置及锁文件保留提交 `5ce4040` 的字节基线，避免用旧设计覆盖最新微调。项目规则补充 API 阶段说明及现有验证行为描述，文档和离线检查补齐交付缺口。本轮没有创建真实 Issue、修改远程标签、发布票集或创建 PR。

工程验证命令：`npm run workflow:check`、`npm run check:all`。前者验证配置、Git 身份、依赖及全部 skill 文件锁清单和哈希、自有 skill/common 的相对 Markdown 链接；后者还运行类型、lint、格式、单测、workflow 回归、构建和 Chromium E2E。Python 3 用于精确内容哈希回归。

新增回归覆盖漏锁文件、遗漏锁条目、哈希正确但链接断裂、跨目录迁移后目标仓库身份适配，以及精确 UTF-8/CRLF/JSON 字段哈希。它们检查基础设施行为，不宣称证明代理必然遵循全部自然语言协议。

## 首次目标项目验收

接入者应在授权的目标仓库验证以下场景并记录具体对象、批准版本及结果；本轮未执行这些远程操作：

1. 完整需求、缺 API 的需求、低于最小输入门槛的需求，以及已有外部 Issue，分别验证澄清和承载路径。
2. 完整规格批准后人工启动规划，核实至少一票、全量批准、父子和阻塞关系；未授权实现时不得自动开工。
3. 完整授权票集包含独立票和依赖票，核实隔离编码、串行集成、验证失败不推进依赖。
4. 暂停、未知远程写入、同一规格纠错、增量范围，以及进程中断恢复；核实人工恢复授权、读回和内容身份。
5. 独立双轴审查、修复复审、最终 HEAD 门禁、正式 PR 关闭引用，以及 PR 后所有权和干净性约束下的清理。

历史研究试验见 [POC 记录](poc-validation.md)。历史通过不能转移为当前仓库、宿主或 GitHub 权限的通过；失败、阻塞、未执行分别记录。可交付的离线模板与完成目标环境端到端验收是两个不同结论。
