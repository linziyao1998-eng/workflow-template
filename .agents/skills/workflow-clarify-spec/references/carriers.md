# Specification carriers

## Workflow-created Issue body

Adapted from Matt to-spec. Use these seven headings; only include decisions and requirements supported by sources/discussion. Describe behavioral interfaces rather than fragile source file paths. A prototype snippet may be included if it encodes a confirmed decision more precisely than prose, with provenance.

1. `## Problem Statement` — user's problem and source of truth.
2. `## Solution` — intended user-visible outcome.
3. `## User Stories` — numbered actor / capability / benefit stories covering the agreed scope.
4. `## Implementation Decisions` — agreed interfaces, data/API contracts, architecture and interactions.
5. `## Testing Decisions` — observable acceptance, existing/highest appropriate test seams, regression evidence and approved verification strategy.
6. `## Out of Scope` — explicit exclusions.
7. `## Further Notes` — versioned source references, remaining questions when incomplete, recorded source provenance.

Create with a preassigned `<!-- workflow-source:<stable-id> -->` marker in the initial body and persist it locally before remote creation. Keep it in future approved snapshots. Resume by exact marker/ID. Before first full approval, the entire body including this marker is the candidate version.

## External Issue comments

Adapted from Matt triage. Start triage-generated comments with:

> *This was generated by AI during triage.*

Working comment: `## Triage Notes`, followed by **What we've established so far** and **What we still need from you** with concrete questions and verification results. Existing Issue body remains unchanged.

Final comment: `## Agent Brief`, with **Category**, **Summary**, **Current behavior**, **Desired behavior**, **Key interfaces**, **Acceptance criteria**, **Out of scope**. Include necessary sources and test decisions so the Brief is a complete behavioral contract. Include a stable `<!-- workflow-brief:<stable-id> -->` publication marker before displaying for approval. Approval metadata goes in a separate comment; do not embed a self-referential hash.

For rejected enhancements only, record concept, reason and related issues in the configured rejection knowledge base. Already implemented requests and rejected bugs do not create that entry. Human decisions to reconsider old rejections override stale notes; record the changed decision faithfully.
